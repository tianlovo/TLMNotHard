# 原版自然睡眠可行性采集

本工具在固定的上游 TLM 提交 `8a3ac5e9eacf0c6d63adf8832949f3ce81484fe6`、Minecraft 1.20.1、Forge 47.2.0 与 Java 17 环境中运行，通过原生 GameTest 服务端观测完整 `Brain` 的自然执行，不启动客户端，也不加载移植版 JAR。
该采样对应 `B10` 离线主人家园睡眠的基础可行性探查，完整 `B10` 验收、跨版本移植等价及统计收益均未在此准入。

## 输入与执行

`contract.json` 定义了三只全新女仆各 150 帧的观测窗口、30 tick 原生 POI 预热、`NIGHT` 日程与 `6000` 世界日时、家园锚点以及北向女仆床。
场景仅绑定离线主人 UUID，不构造在线玩家实体，且不重置世界或实体 RNG。
受测实体使用精确的原版 `EntityMaid` 类注册进真实世界并随自然 tick 推进，实际 `Brain` 活动在 `core` 与 `rest` 之间自然切换，不手动调用 `Brain`、寻路接口或直接改写睡姿字段。
探针在每个 `LevelTick` 的 `END` 阶段记录出生后 `1～150` 帧的实体年龄、当帧 `LivingTick` 次数、坐标、速度、睡姿标志、床占用状态与当前活动。
采集结束后仅清理本轮新建实体并恢复世界日时与规则，独立的 GameTest 临时世界不复用任何玩家存档。

## 构建与运行

请仅在既有的独立原版参考 checkout 上应用本目录的 `reference.init.gradle`，切勿将其用于 GTNH 移植工程。
该脚本继承已审批的原版工具链锁与源码完整性检查，保留既有客户端观测补丁，并单独建立选定类集合、身份清单与工作目录：

- `TLMNH_REFERENCE_PROBE`：指向既有动画参考工具目录。
- `TLMNH_SLEEP_NATURAL_PROBE`：指向本目录。
- `TLMNH_REFERENCE_HOME`：源码仓库外的原版运行根目录，实际工作区位于其下的 `sleep-gametest` 子目录。
- 既有的 Git、Java 17 与工具链锁配置继续生效。

主要 Gradle 任务为 `prepareSleepNaturalReferenceIdentity` 与 `runGameTestServer`。
后者使用 [Forge 原生 GameTest 服务端入口](https://docs.minecraftforge.net/en/1.20.x/misc/gametest/)，仅启用本工具注册的测试命名空间。
结构模板采用本工程生成的 `17×8×9` 空 NBT，测试初始化阶段在模板内铺设石质平台与原版女仆床。

## 检查与边界

```text
python tools/sleep-natural-reference/check.py capture.json --build-identity sleep-natural-build.json --agent sleep-definition-agent.jar
```

采样输出位于外部工作区的 `captures` 目录，构建身份清单位于外部根目录下的 `identity/sleep-natural-build.json`。
检查器会依次校验合同哈希、实际编译资源、只读 agent 与清单绑定、首次类定义记录、三只独立新实体及 450 帧完整性，随后汇总各轮首次入睡帧号。
复核历史样本时，`--tool` 参数必须指向当次采样对应的冻结工具源码目录，后续工具迭代不能改写历史样本的输入身份。
类定义字节摘要与资源字节摘要分列记录并据实报告差异，不单凭摘要一致宣称已解释全部服务端类变换或整套 classpath 等价。
采样完成或 GameTest 进程退出成功仅代表观测链路跑通，评估结论固定保持 `NOT_EVALUATED`，不会自动升级为完整 `B10` 或移植验收通过。
进程强杀、崩溃原子回滚、多人联机与正式统计显著性验收不在当前基础采样范围内；五机制成对探索见下文。

## 移植侧观察

`tools/horizon-qa` 中的 `NaturalSleepPortTests` 复用同一份合同，在独立的 Horizon-QA 测试世界中分别运行完整忠实模式 `F` 与增强模式 `N`。
用例直接绑定离线主人 UUID，不构造玩家实体，并在移植侧逐项校验家园三类活动锚点、6 格睡眠搜索范围、世界日时、北向女仆床及初始出生位置。
每组观测三只全新女仆各 150 帧；采样成功仅代表观测记录完整，若出现未入睡或轨迹异常不会误判为功能通过。

`compare_port.py` 接收原版采样、冻结原版工具/构建身份/agent、两份移植端采样、实际玩法候选与 pilot JAR，以及 Horizon-QA 状态 JSON、`observed` 记录和 JUnit 报告：
- 原版侧参数：`--original-capture`、`--original-tool`、`--original-build`、`--original-agent`。
- 移植侧参数：可重复传入的 `--port-capture`，配合 `--candidate-jar` 与 `--pilot-jar`。
- 运行与输出参数：`--hqa-result`、`--observed`、`--junit` 与 `--output`。

检查器在核验资源身份、策略工厂选择、自然 tick 连续性及场景清理后，仅输出首次入睡帧、睡眠总帧数、床头水平偏移、高度及位移范围等描述性指标。
由于早期基础合同尚未完整冻结初始场地细节与天气输入，世界 RNG 和跨版本物理差异同样未受控，比较结果固定保持 `NOT_EVALUATED`，不授予完整配对输入、`B10` 或统计准入。
追加 `--require-stable-sleep` 可单独核查无干扰基础睡眠姿态：入睡当帧位于床头高度 `+0.8`，后续帧稳定在 `+0.5625`、水平居中、零水平速度且持续持有自身床位。该门禁先在 Indev159 的故障轨迹上成功检出下落与滑移，随后才用于验证修复候选，不据此反推整套睡眠行为或寻路收益通过。

## 177 定向修复验证

新版合同显式固定 `HARD` 难度与初始空库存、零药效状态：原版在独立世界中设置并恢复难度，移植侧核验实际运行难度，两端同步记录非空物品槽数与活跃药效数。
原版首次定义观测集合扩充至 12 个类（纳入真实的 `MaidPoiManager`），移植侧则额外校验行为协调器与共享睡眠资源所有者的包内类资源。
检查器支持追加 `--require-paired-inputs --require-immediate-hurt-wake`：前者限定校验已列明的标量字段、家园配置、任务、语义方块布局及空库存/零药效前提；后者核验受到 `generic` 伤害后当即清除睡姿与床占用，并在下一自然帧保持清醒。
Indev176 的历史 `F` 与 `N` 样本均被该即时唤醒门禁准确拦截，修复后的 Indev177 在原版、`F`、`N` 三端全部通过，五种机制合计 15 只女仆、3600 帧记录完整；完整初始 NBT 等价与共享随机流仍标记为 `false`。
对完整初始 SNBT 的逐项审阅还识别出随机 `Rotation` / `SoundPackId`、`Fire` 默认值、列表/属性/库存编码格式、任务附加数据及跨版本平台字段差异；进入正式统计测评前仍需冻结可控输入并逐项完成语义审查，不能把选定标量一致等同于全实体状态一致。

本工具原创代码沿用项目许可证，固定上游源码及复用的只读身份观察 agent 各自保留原有来源与许可声明。

## 五机制成对探索

`paired-contract.json` 配合 `SleepMechanismGameTests` 与 Horizon-QA 侧的 `SleepMechanismPortTests`，独立于早期的三女仆基础采样合同运行。
显式设置 `TLMNH_SLEEP_PAIRED=true` 时，原版启用独立命名空间 `tlmnh_sleep_paired` 与 `sleep-paired-gametest` 工作目录，并将结构模板同步复制到该命名空间下，避免被 Forge 按模板域过滤成零测试。
五种成对机制依次覆盖正常入睡、床位占用后释放、床位不可达、入睡后拆床以及睡中受击，每个场景新建一只自然女仆连续观测 240 帧。
受控占床演员仅用于构造床位占用输入，不替代受测女仆：移植侧使用真实的床 `TileEntity` 租约，原版侧使用真实的床方块占用状态。
由于原版 `MaidPoiManager` 仅注册未占用的床头方块，占床场景出生时的实际可用 POI 数为 `0`，其余四个场景为 `1`；工具如实记录该行为，不伪造额外 POI 去迁就旧断言。

原版 `LevelTick` 与移植侧 `WorldTick` 均在当帧状态记录完毕后再施加外部干预，同步保存干预瞬间的睡姿、血量、床占用状态及后续自然恢复轨迹。
中途未入睡或未满足干预前置条件的样本均原样保留，GameTest 框架退出成功仅代表采样流程结束。
新版捕获文件额外保存实际方块布局、实体属性、天气、世界难度与完整初始 SNBT；`compare_mechanisms.py` 依次核验选定类资源、原版首次定义、合同摘要、完整根策略 `F/N`、自然 tick 序列、15 只独立实体身份及 HQA/JUnit 结果，将输入差异与各机制表现分列报告。
具体命令行参数见该脚本的 `--help`；复核历史数据时须传入当次冻结的工具目录，不用新版脚本源码覆盖历史输入身份。

Indev176 完成了原版 5 例与完整 `F/N` 10 例共 3600 帧采样：当时原版难度为 `EASY`、移植侧为 `HARD`，其余已纳入比对的标量、家园与语义布局一致，完整 NBT 与库存语义尚未准入。
该轮观测到原版受击后当帧醒来，而 `F` 延迟 10 帧、`N` 延迟至下一帧醒来；上述行为差异连同首轮零测试、旧 POI 断言导致的 3 例失败均独立归档保留，未将采样跑通包装成机制等价。
完整 `B10` 验收、跨版本同随机流/物理校准、非劣效容忍余量与统计显著性结论均维持 `NOT_EVALUATED`。

## 实际出生输入

五机制合同在原版与移植侧的真实出生入口处统一固定 `yaw`、`pitch`、头部与身体朝向及其插值前值，并显式指定同一音包 ID。
采集器同时记录实体内存字段与从同一份完整 NBT 反序列化读回的 `Rotation` 和 `SoundPackId`，防止仅调用了辅助函数却未真正落入实体状态。
检查器追加 `--require-deterministic-spawn` 后会核验上述朝向与音包字段，并校验移植侧初始化辅助类的实际 JAR 资源哈希。
早期的三女仆基础合同不启用该确定性出生钩子，历史冻结样本继续搭配各自的旧版检查器复算，且不重置或假定跨版本共享同一随机流。
该项校验通过后继续推进后续功能开发，完整实体属性、平台附加字段与跨版本物理差异的语义审查仍单独维持未准入状态。

## 统一战斗任务的输入比较

`compare_combat_mechanisms.py` 与 `compare_combat_boundaries.py` 支持显式传入 `--unified-tasks` 选项。
在该模式下，增强组远程战斗输入须同时具备统一战斗任务 ID、版本 `1` 的强类型任务状态、待消费的远程武器偏好标记，以及一把真实零磨损原生弓的保护快照。
原版、忠实模式 `F` 及近战输入继续按各自的原始任务 ID 校验，完整初始输入、逐帧策略身份、物理环境分组、装备耗材、安全门禁与场景清理检查一并参与核对。

不加参数时默认执行旧版分任务合同检查；开启 `--unified-tasks` 后会输出独立版本号的统一任务比较报告，并完整记录原始任务 ID 与映射依据。
原始采样压缩包与历史比较器的失败报告均独立保留，完整运行参数可通过对应脚本的 `--help` 查看。
