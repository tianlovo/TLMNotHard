# 原版 TLM 1.20.1 动画对照实验

本目录是面向原版动画参照的独立实验入口，用于运行 Minecraft 1.20.1 及对应版本的上游原版 Touhou Little Maid（TLM）。
GTNH 移植模组本身仍以 Minecraft 1.7.10 为目标平台，本目录下的 Java 17 采集探针不进入模组源码集或分发 JAR。

小样本阶段已在真实的原版客户端上采得两条动画管线的基准轨迹：汉服酒狐（115 根骨骼）与 Bedrock 酒狐（126 根骨骼）各 30 帧，全程无模型回退。
实测加载的模组列表仅包含 Minecraft、Forge 与上游 TLM，首次只读采集阶段未改动任何上游源码。
受控原版 A/A 重复性校验已通过：两个模型各独立重建三次、每次采样 30 步，四组逐字段比对零差异；注入真实执行路径的骨骼位移、内部时钟与片段选择三类故障也均被自动检出。
两份空手待机样本已完成移植端 CPU 重放，修正控制器启动与循环计时后均实现逐值一致；后续补充的动作转换合同与有界离屏 FBO 实验结果见下文，通用动态输入与完整世界渲染成像仍待后续覆盖。

## 受控动作转换实测

在待机基线之上新增了 `idle_walk_idle` 小样本实验：两个模型各自独立重建三次，每次连续推进 72 步（依次为 24 步待机、24 步走动、24 步待机）。
原版侧四组 A/A 比对差异为 `0`，采样期间汉服酒狐有 27 根骨骼、Bedrock 酒狐有 6 根骨骼随时间发生变化。
汉服酒狐主控制器在第 `23` 步处于 `idle`、第 `24～47` 步切入 `walk`、第 `48～71` 步回到 `idle`，全程由真实输入条件触发状态切换，未人工硬编码指定目标动画片段；每一步的输入钩子与原版 Gecko 更新返回值均经过严格核验。

移植端 CPU 重放中两个模型均逐值对齐，真实注入的 `Head` 骨骼位移负例以及缺失 `groundSpeed` 字段时的 Java 端拒绝检查一并通过。
实验结果独立保存至 `aa-idle-walk-idle-experiment.json` 与 `ab-idle-walk-idle-experiment.json`；参考客户端在采样完成后正常保存退出，而非仅在离线状态比对人工拼装的 JSON。

需注意该场景仍属于原地运动学动画夹具：步态相位、速度标量与 `previous position` 按受控合同同步推进，实体世界坐标并未发生真实位移。因此该结果不构成真实世界移动、寻路导航、实体快照绑定、非零头部转向、随机动作、手持装备或 GPU 成像的验收证明，`approved_for_bulk` 标志继续保持 `false`。

## 非零头转向与真实绑定实测

`head_turn` 合同继续沿用上述两个模型，共分四段推进 72 步：零角、`yaw=30 / pitch=15`、`yaw=-45 / pitch=-20` 以及回到零角（角度单位均为度）。
原版侧各独立重建三次，四组 A/A 比对差异为 `0`；移植端 A/B 重放同样逐值一致，且 `Head` 位移注入负例与缺字段拒绝检查均通过。
采样深度上，Gecko 路径分别记录核心动画、头部附加偏转与最终合成姿态三层快照（第 `18～53` 步头部层发生实质变化），而 Bedrock 路径仅比对外部真实可观测的最终骨骼姿态；重放器同时验证开启可选的核心层观察点不会改变同输入播放器的最终输出，且不强求不同内部动画阶段的中间表示彼此相等。

由于纯 CPU 重放直接从采集 DTO 构造动画输入，仍会绕开 GTNH 2.9.0 客户端真实的渲染取帧代码，本轮还在真实 RC2 客户端内补充了 6 个输入链绑定用例：涵盖 Gecko 正负角、故意回退旧符号规则的故障负例、修复后符号恢复，以及 Bedrock 正负角，全部按播放器实际消费的数值判定。
实测中故障用例准确返回 `bindingMatched=false`、恢复用例返回 `true`，每轮测试结束后均完整还原实体的 8 个角度字段，未通过事后篡改落盘 JSON 来伪造负例。
该客户端探针从真实的实体字段出发，经由原生 `RendererLivingEntity` 计算渲染参数，再拦截读取动画播放器实际消费的 `query` 值；正是通过这项端到端核对，定位并补齐了真实渲染路径上的符号换算规则（Gecko 的相对 `yaw` 经 `wrap/clamp` 后与 `pitch` 一并取反，Bedrock 则保持正号）。

这 6 个绑定用例仅覆盖上述两个模型与固定头部角度，尚未覆盖移动速度、主副手槽位、全量实体快照字段、复合动作或最终屏幕像素。同轮完整候选联调中还出现了一项命名牌开窗夹具失败，整轮记录按规保留失败状态，不会把局部通过的 6 个头转向用例包装成整包候选通过。
这轮排查也印证了分层验证的必要性：离线冻结轨迹负责锁死纯数值计算，真实客户端绑定探针负责打通实体到 `query` 的输入链，而离屏/实机 GPU 检查则用于兜底提交桥之外的成像盲区。紧随其后的 `indev.31` 仅补齐了命名夹具缺失的内存网络通道，使服务端命名复测通过，期间未触碰生产渲染输入链，也未重跑动画与客户端实验；首轮失败记录原样归档，真实客户端的命名发包与界面交互仍留待后续验证。

## 长期维护的决策

原版 1.20.1 客户端仅用于采集独立的权威参照，日常开发回归以消费离线冻结输入的纯 CPU 重放为主。
项目不采用“两个版本客户端同时播放录像按帧号比对”或“跨版本直接比对截图差异像素数”作为移植正确性的判据：跨引擎的时间轴抖动、光照模型与渲染后端差异极易干扰问题归因，即便肉眼看着相近，也只能说明当前受测片段未暴露明显异常。

截至目前，仅确认上述两个代表模型在受控待机、原地走动转换、非零头转向 CPU 重放及指定角度真实客户端输入绑定上工作正常，尚未放行全量内置模型的批量自动化验收。
两个模型各自三次独立重建、每次 30 步的原版 A/A 完全可重复且骨骼随时间动态演进，对照实验也确实抓出了移植版早期的启动过渡与循环取模时序偏差，并验证了真实代码路径上的故障可检出——这些证据足以说明工具链有效，但不能外推为全部动作、随机分支、物理耦合或最终画面均已对齐。真实 RC2 客户端目前仅有头部角度绑定的正反例，移动速度、穿戴装备及其他实体快照字段的绑定仍待逐项补齐；DTO 字段回显一致不代表运行时取值链路无误，不能靠堆砌离线 DTO 样本数量替代真实客户端输入链验证。

| 层次 | 主检查 | 当前边界 |
| --- | --- | --- |
| 原版采集 | 资源、输入、更新序列和原版 A/A | 两模型的受控待机、原地走动转换和头转向 |
| CPU 重放 | 控制器及分层局部姿态，输出首个分歧 | 父级累积矩阵、完整动作和通用随机合同未验证 |
| 实际输入绑定 | 实体、原生 render 参数和实际消费 query，真实错误负例 | 已测指定头部角度，速度、装备等仍待验证 |
| 提交桥 | 真实 RC2 的顶点参数、UV 与纹理绑定，故障注入后恢复 | 预期流共用几何函数，不是独立几何或 GPU 结果 |
| 实际成像 | 固定 RC2 环境的截图或离屏图，检查缺件、透明与状态污染 | 两模型固定姿态无 shader FBO 矩阵负例已测；世界渲染、完整材质和 shader pack 仍未验证 |
| 双端玩法 | 实际客户端请求、服务端权威状态与同步 | 单独运行，不由动画回放推导 |

恒定步长的 `idle -> walk -> idle` 与非零头部转向通过有界实测后，后续仍以这两个模型为锚点，下一步再单独引入非均匀时间步长或受控随机源。
所有正例中的动作切换必须由真实输入条件驱动控制器自然选出，严禁直接指定目标片段名绕过状态机条件；同时严格区分“原地构造步态参数驱动动画”与“世界内真实位移”，分开记录 `limb` 摆幅参数、实体速度与位移查询，不把动画回放用例混同于跟随或导航 benchmark。
每新增一份合同，均须先完成原版三次重建 A/A 校验，再接入移植端 A/B 比对；基础确定性合同稳固后，再逐项叠加头转向、非均匀步长与随机种子。涉及二阶物理或状态累积时必须重放完全相同的更新步长序列，不能只对齐终点时刻，不同步长序列之间也不强求中间姿态相等。凡遇到缺失输入字段、未拦截的随机数调用或原版自身 A/A 不稳定的情况，一律返回“不可判定”，严禁填零兜底或放宽数值容差。

对于确因机制原因无法做严格逐帧数值重放的输入，应明确收窄精确数值比对范围，改用受控短片段、几何/状态不变量及同一 RC2 渲染环境下的离屏图像回归兜底；替代检查同样必须配套真实故障注入负例并写明未覆盖盲区，不能把“不可判定”静默改判为通过。
跨版本截图对比仅用于排查模型缺件与严重破面，像素级回归基线只在同一套完整锁定的本机渲染环境内有效。
在成像层落地上，优先针对顶点提交桥观测不到的外层盲区设计实验——例如保持提交桥内部的局部顶点流完全不变，仅人为篡改外层 OpenGL 模型矩阵或全局混合透明度，检验离屏画面检查能否准确报警。其中外层缩放矩阵负例已在无光影包的离屏 FBO 中跑通，独立像素分析成功检出面积坍缩并在恢复后回到零像素差；世界渲染矩阵与全局透明度盲区仍待后续覆盖（既有提交流 `trace` 未记录外层 OpenGL 矩阵栈，且预期流与实测流读取同一当前全局颜色，因此无法单独承担此类检查）。

| 变更 | 默认测试范围 |
| --- | --- |
| 仅文档或 IDE 配置 | 对应文本、路径或配置检查 |
| 动画计算、控制器、查询或动作绑定 | 受影响的冻结 CPU 轨迹与故障负例 |
| 几何、UV、材质、装备或渲染接口 | 对应 CPU 检查及真实 RC2 渲染场景 |
| 上游、资源、探针或输入协议 | 新版本原版 A/A、故障检出和 A/B，保留旧基线 |
| 发布候选 | 必需动作、35 酒狐逐项、其余内置模型和双端矩阵 |

日常开发不为每次 `git push` 启动双端游戏客户端，也不对未发生变动的上游参照重复采样。
每轮实验均须完整登记源码提交、资源哈希、探针版本、输入合同、运行环境、实测耗时与证据摘要。目前参考端身份校验已自动比对真实 Git `HEAD`、精确补丁、工具链锁以及 20 个核心类的首次定义/资源哈希，既不轻信表面配置标签，也不夸大为整个 JVM classpath 等价；受限于小样本规模，当前耗时与误报数据不作为全量回归的固定预算承诺。
体积较大的原始采样轨迹、运行存档与截图统一存放在源码仓库之外，严禁向版本库提交任何本机绝对路径。核心所需的 18 份基准轨迹与标准资源已打包为约 `2 MiB` 的只读冻结包，由仓库内 `catalog` 锁定 `manifest` SHA-256，日常离线 CPU 回归不再依赖本机安装原版 1.20.1 运行目录；在已有本地 Gradle 依赖缓存的前提下，独立干净克隆配合 `Gradle --offline` 已验证通过，跨机器浮点误差预算与冷缓存纯离线构建则尚未验证。

由于上游 1.20.1 参考工程的构建脚本包含 ForgeGradle 版本区间、Librarian 动态映射及 MixinGradle `SNAPSHOT` 依赖，仅固定上游 TLM 提交号不足以锁死整个构建工具链。为此本目录建立了冻结基线包与工具链锁清单，逐项记录实际解析到的构建插件 JAR、采集探针、补丁、重放器与比较器哈希；后续一旦升级工具链，必须显式建立新版本身份锁。请求回执与采样输出现已同时记录磁盘来源、启动 `manifest` 及 20 个核心类的运行时首次定义摘要（资源字节与定义字节分列保存，覆盖集合之外不做外推）。当新结果与既有基线出现偏差时，须先保留旧基线、定位根因并登记变更依据，不得顺着移植端现有输出反向刷写基线或调大容差。目前仓库仅配置了按文档路径触发的轻量 CI，尚未部署云端动画或 GPU 测试流水线，也不会把耗时较长的实机游戏回归挂到每次普通推送上。

在人机分工上，自动化工具负责做第一道故障分流、定位首个分歧帧与最小化复现场景，由开发代理复现并核查关键差异帧；不要求用户日常逐个模型肉眼轮播检查，但玩法交互取舍、难以数值化的视觉观感以及正式发布前的最终把关仍由人工裁决。增强行为 AI 则另行通过任务成功率、响应延迟、异常恢复与服务端耗时预算做专门的业务 benchmark，不追求逐 tick 复刻原版 AI 的内部随机分支。

上述分层验证思路参考了 [Riot Games 的确定性录制重放与首分歧定位实践](https://www.riotgames.com/en/news/determinism-league-legends-fixing-divergences) 以及 [OpenUSD 将常规数值比对与显示设备渲染测试解耦的测试指南](https://openusd.org/24.08/api/_page__testing__guidelines.html)；外部实践仅作方法学借鉴，具体方案在本项目是否成立一律以实测数据为准。

## 选型与限制

### 冻结包和身份工具的实现进度

新增的 `baseline_bundle.py` 负责导出与校验完整的 18 份压缩采样轨迹、标准参考资产、构建身份记录及工具链锁；导出操作生成独立归档，不修改仓库既有的 `catalog` 记录。消费冻结包时，脚本先核对外部硬编码锁定的 `manifest` SHA-256，再逐文件校验压缩流与解压后原始字节、相对路径、文件大小、18 份原版 A/A 重复性及运行时类身份。包内附带的标准参考资产仅服务于 Python 侧交叉核对与依赖追溯，既不挂载进 Java 编译/运行 classpath，也不会覆盖当前模组的生产资源。缺少新版运行时身份字段的早期采样包会被导出器直接拦截，防止事后把仅记录了配置提交号的历史样本包装成经过首次类定义校验的权威基线。

参考端构建脚本同步新增了 `tlmnhReferenceIdentityInventory` 任务，将实际解析的 Gradle 插件工件与任务实现类的 `CodeSource` 分列导出（`INVENTORY_ONLY` 模式仅做盘点，不代表审批放行）。经人工核查生成外部 `APPROVED` 锁文件后，`tlmnhReferenceRuntimeIdentity` 与 `runClient` 会逐项强校验工具链锁、固定上游源码与补丁、采集探针及 20 个核心类的编译字节。配套的极简只读 `premain` 观察器在类加载时记录首次定义输入字节，与类路径资源摘要分开存档；该机制明确限定在“挂载单一启动 agent、禁用动态 attach、无运行时类重定义”的受控参考环境内，不宣称证明整套 classpath 等价。独立单测任务 `testReferenceIdentityAgent` 会在单独的 Java 17 子进程中验证真实的 `premain` 挂载、启动 `manifest` 绑定及缺项拒绝逻辑，无需启动游戏客户端。

本阶段实测中，离线工具链盘点、独立 agent 单测夹具、严格参考端构建以及真实客户端内 20 个核心类的身份核验已全部跑通；其中有 5 个类在经 Forge 加载器转换后的首次定义字节与原始资源字节不同，报告将两类哈希严格分列、未做混同。
重放编排脚本 `bundle_regression.py` 在执行一次 `prepareReferenceReplay` 编译准备后，会为每个测试用例拉起独立的 Java 25 子进程，逐次记录生产类与资源的实际加载来源及编译摘要，并严防测试 classpath 上的同名类遮蔽生产类。正常重放正例、真实 `Head` 位移注入、Java 端缺字段拒绝与未知协议版本拒绝四类结果分项统计，不会拿外层压缩包哈希损坏拦截去冒充 Java 动画引擎内部的语义负例。此外，“干净仓库克隆 + 既有本地 Gradle 依赖缓存”的 `--offline` 回归与“全新裸机冷缓存纯离线构建”分开定义，当前仅验收前者。

新纳入的三份原版合同（每个合同覆盖两个模型×三次独立重建）在原版 A/A 复检中全部零误差；完整的 18 份采样与标准资产打包后体积约 `2 MiB`，已通过 `manifest` 哈希锁定为 `tlm1201-core-v1`。在原版源码 checkout 与外部 `runtime` 目录均不存在的全新干净克隆上，仅凭既有 Gradle 缓存执行一次 `--offline` 编译准备后连续拉起 13 个独立 Java 25 进程：18 份原版 A/A 复核、6 个跨版本重放正例逐值对齐、3 个骨骼位移负例、3 个缺输入拒绝与 1 个未知协议拒绝一次全过，10 个必需生产类及当次 `main` 编译产物的来源路径与前后哈希也全部吻合；针对压缩包字节篡改、未知 schema 与重复原版采样注入的完整性拦截单测同样独立通过。该轮本机实测总耗时约 `59` 秒（仅作单机记录，不构成跨平台或 CI 配额承诺，亦不代表已验证冷缓存构建或操作系统级断网隔离）。

当前获批的 `catalog` 仅覆盖这 6 个 CPU 动画夹具；本地依赖缓存就绪后可执行以下命令（每次运行请指定全新的 `--output` 目录名）：

```console
python tools/animation-reference-1.20.1/baseline_bundle.py verify --id tlm1201-core-v1
python tools/animation-reference-1.20.1/bundle_regression.py --id tlm1201-core-v1 --offline --output build/reference-replay-run-1
```

除纯 CPU 轨迹外，两个酒狐模型还在真实的 GTNH 2.9.0 客户端内完成了同一姿态、同一离屏 FBO 渲染事务下的五样本矩阵盲区实验（三次正常渲染 → 外层矩阵缩放 `0.5` → 恢复正常）：期间提交桥记录的局部顶点流摘要完全不变，三次正常渲染之间像素零差异；注入外层 `0.5` 缩放后，汉服酒狐与 Bedrock 酒狐的非透明像素占用面积分别从 `16144` 降至 `4029`、从 `14672` 降至 `3666`（独立 Pillow 脚本从导出的 RGBA PNG 底部原点复算像素哈希、非空像素数与包围盒，实测面积比精准落在约 `0.25`），恢复正常矩阵后像素再次零差异对齐，且后续常规头部绘制与 OpenGL 状态还原均验证无残留污染。需明确该实验属于关闭光影包、手动设定正交/透视投影的固定姿态离屏测试，不代表已覆盖世界内 `RenderLiving` 完整矩阵链、其他动作片段、全量材质状态或跨版本 GPU 画面等价。首轮实测曾因测试实例默认启用了光影包导致离屏 FBO 零采样并返回 `INCONCLUSIVE`，该原始报告已原样归档保留，未删改门禁；随后在完整备份专用测试配置、临时关闭光影包后完成有效实测，并在测试结束后原样恢复了配置文件。综上，现阶段仍不放行全模型批量自动化验收，后续还需逐步补齐独立静态几何对照、完整动态输入链及真实世界/光影场景验证。

整体路线上，项目坚持先打通“原版真实轨迹采样 → 移植端同输入重放 → 分层骨骼姿态差分”，再向上叠加双端真实渲染检查；避免一开始就让两个版本世界同时跑录像再按帧号截屏对比，导致渲染帧率抖动、随机数漂移、物理步长与坐标系差异混杂在一起无法拆解。冻结关键帧关节变换做确定性回归可参考 [Mohr-Daurat 等人在 SCA 2017 的动画回归实践](https://doi.org/10.1145/3099564.3106641)，结构化状态日志与首分歧二分定位则可参考前述 [Riot Games 工程总结](https://www.riotgames.com/en/news/determinism-league-legends-fixing-divergences)。

## 观测器协议

当 JVM 显式传入 `-Dtlmnh.referenceProbe=true` 时，`ReferenceObservationProbe` 会在客户端每 tick 轮询读取游戏目录下 `tlmnh-reference/control/*.json` 中的指令（单 tick 最多消费 4 条），执行回执写入 `responses/`、采样数据写入 `captures/`，所有落盘均采用“先写 `.tmp` 临时文件再原子重命名为 `.json`”的方式：

| 请求 | 作用 |
| --- | --- |
| `{"command":"status"}` | 返回实际游戏版本、世界/玩家状态、当前界面及已加载模组清单 |
| `{"command":"create_lab"}` | 创建全新的纯空气虚空实验世界并切入原生旁观模式；同名世界已存在时拒绝覆盖 |
| `{"command":"open_lab"}` | 重新打开已创建的专用参考世界 |
| `{"command":"clear_scene"}` | 请求清理带实验标记的测试女仆，需随后结合 `status` 核对场景状态与 `maidCount` |
| `{"command":"reload"}` | 在场景清空后触发异步资源重载，重载彻底完成后才放行受控采样 |
| `{"command":"spawn_case","model":"geckolib:winefox_hanfu"}` | 在参考世界准备支撑平台并生成指定模型的原版女仆，拿到返回 UUID 后需再核对 `scene` 就绪态 |
| `{"command":"observe","entityUuid":"指定女仆UUID","frames":30}` | 连续采集指定女仆接下来实际渲染的若干帧，有效范围为 `1～240` 帧 |
| `{"command":"sample_case","model":"geckolib:winefox_hanfu","frames":30,"seed":424242,"fault":"none"}` | 自动执行清场与资源重载后，新建受控实体并从首次渲染起连续采样 |
| `{"command":"shutdown"}` | 请求参考客户端正常保存并退出 |

`observe` 与 `sample_case` 受理后先返回 `waiting-render`，`reload` 受理后先返回 `waiting-reload`，待后台任务彻底完成后才更新为 `complete`；若 `60` 秒内未采满目标帧数则标记为 `failed`（Python 控制端单次轮询同样设有超时上限）。场景变更类指令返回瞬间的 `ready` 字段仍为 `false`，调用方必须继续轮询 `status` 直至 `scene` 变为 `ready`，中途任何异常都会原样保留在错误字段中。测试女仆全程关闭行为 AI 并锁定观测坐标，专用于动画管线采样，不充当行为 AI 测评场景。采样记录涵盖原版当前模型 ID、骨骼变换与可见性，Gecko 模型额外导出活跃动画片段、控制器状态机阶段与时间偏移，Bedrock 模型则额外导出四元数与位移偏置（不能仅凭欧拉角还原完整骨骼姿态）。

现行输出格式标记为 `observation-v0`：常规 `observe` 仅记录渲染末态 `render-post`，而受控模式下的 Gecko 采样会同时保存核心动画层、头部偏转层与最终合成骨骼三组快照。常规观测记录中 `allInputsCaptured` 与 `equivalenceVerified` 固定为 `false`，不可将其视作任意自然游戏过程的完整可重放输入。
受控采样模式额外打上 `controlled-idle-v0` 协议标记，统一锁死实体 UUID、随机数种子、逻辑 `tick`、`partialTick`、着地标志与头部欧拉角；每轮采样前强制清场并重载资源，渲染期间临时覆写的实体字段在当帧绘制结束后立即还原，且离散采样步序号不等同于真实墙钟帧间隔。其配套输入块标记为 `controlled-empty-idle-v1`，完整记录实测状态、Molang `query` 读值与渲染调用参数；目前重放器仅放行上述两个空手模型的待机、原地走动转换与非零头转向三份受控合同，遇到字段缺失、未经审查的活跃动画片段或额外叠加动作层时一律拒绝执行，绝不将未知输入静默填为 `0`。

资源一致性校验严格贴合上游真实的资源加载路径：核对唯一默认内置包解包后的原始文件以及常规资源管理器加载的默认 Gecko 动画文件；一旦检测到启用了多个模型包则立即拒绝运行受控合同，防止其他第三方包内的同名模型污染原版基线。移植侧资源字节必须与固定 Git 提交中的原始字节完全相等；参考端加载的有效 JSON 允许存在可精确复算的纯 LF/CRLF 换行符差异，而 PNG 贴图等二进制资产则必须逐字节一致。工具绝不放过任何实质性的 JSON 内容差异，也不会把“磁盘资源文件哈希一致”等同于“运行时贴图绑定与 UV 绘制无误”。

采样钩子在渲染线程仅做只读拷贝并写入有界内存列表，实际磁盘落盘推迟到客户端逻辑 `tick` 阶段完成；即便如此，探针本身仍可能轻微影响帧间时间间隔，后续扩展动态场景时需持续量化其干扰并复核可重放性。此外，早期首个非受控汉服样本的实测相邻 `seekTime` 步长约为 `0.16～0.30 tick` 且主控制器处于 `jump` 片段，提醒我们不能先验假定普通世界抓帧就是恒定步长的 `idle`；同时上游汉服模型共挂载 28 个动画控制器（其中 `magic_casting` 在受控 30 帧内全程保持 `STOPPED`），比对时不能仅凭移植版未挂载某个静默控制器就直接误判动画计算错误，必须先对齐输入作用域、初始状态与控制器阶段映射。

## 已完成的小样本验证

| 实验 | 实际结果 | 结论范围 |
| --- | --- | --- |
| 原版 A/A | 两模型各 3 次、每次 30 步，4 组对照差异 `0` | 这两个受控用例可重复，不代表全部模型和状态 |
| 排除全冻结假通过 | 汉服 10 根、Bedrock 3 根骨骼随采样步变化 | 并非只比较了静止不动的骨骼 |
| 头部位移故障 | 首个分歧 `frames[0].bones.Head.translation[0]`，`0` 变为 `0.25` | 检出实际绘制前的骨骼偏移 |
| 时钟故障 | 首步期望 `0`、实际 `1`，被内部时钟合同拒绝 | 检出时间输入与引擎推进不一致 |
| 片段选择故障 | 首个分歧 `frames[0].controllers[8].clip`，`idle` 变为 `walk` | 检出实际主控制器选错片段 |
| Bedrock CPU 重放 | 126 根骨骼、30 步，输入与姿态逐值一致 | 仅限该空手待机夹具的局部骨骼 |
| 汉服 CPU 重放初轮 | 首个分歧 `frames[0].controllers[0].state`，`TRANSITIONING` 与 `RUNNING` 不同 | 已定位并修正启动过渡时序 |
| 汉服 CPU 重放复测 | 115 根骨骼、30 步及适用控制器状态/时钟逐值一致 | 恢复原版启动与循环计时，基线和容差未改 |
| 移植版实际位移故障 | 首个分歧 `frames[0].bones.Head.translation[0]`，`0` 变为 `0.25` | 未编辑落盘后的姿态 JSON |
| 缺输入拒绝 | 缺失 `groundSpeed` 时实际 Java 重放拒绝执行 | 不以默认值填补未采集字段 |
| 参考命令 I/O 错误 | 真实制造额外空包目录，`sample_case` 失败后 `status` 仍可用 | 单次命令失败不再拖垮整个轮询器，临时目录正常清理 |

表中所有故障负例均通过真实代码路径上的受控开关注入，未采用事后手工修改 JSON 的假端到端方式。上述结论仅支撑这两个受控模型在对应合同下的机器数值对照，尚未覆盖贴图、UV、OpenGL 状态机或全量随机与二阶物理组合。比较器直接核对原始双精度/单精度输出而不顺着移植端结果放宽容差，跨硬件平台的浮点误差预算以及四元数符号/矩阵正交归一化规则仍需在扩大范围前专门标定；对于原版存在而移植版按需裁剪的 `magic_casting` 控制器，仅当其在原版每一帧均处于 `STOPPED`、未绑定活跃片段且时间游标恒定未动时才允许投影剔除，否则一律判为不可判定。现阶段不批准将该流程直接放大为全量内置模型的批量签收。

## 扩大测试前的门槛

1. 在至少一个 Gecko 酒狐模型与一个 Bedrock 内置模型上稳定采全所需字段，出现任何模型回退或空骨骼树均直接判败。
2. 同一组原版受控输入在新建独立实体实例的条件下至少重复采样 3 次，查清所有重复误差来源与非确定性分支。
3. 移植端完整消费同一份冻结输入轨迹，并覆盖验证受控随机数消费、可变更新步长、游戏暂停与控制器状态清理。
4. 在真实执行链路中人为注入骨骼位移、时钟偏移或片段误选故障，自动化比较器必须准确报错并定位到首个分歧帧与字段。
5. 配套真实的客户端离屏或实机渲染检查，补齐纯骨骼数值重放覆盖不到的贴图绑定、UV 坐标与 OpenGL 状态泄漏检查。

凡属首版明确要求但尚未实现的必需动作，一律不得按“跳过即通过”处理；采样自身不稳定时如实记为不可判定，绝不自动放宽容差或静默覆盖历史基线。待上述五道门槛全部闭环后，再分批推广至酒狐全系列（35 项）及其余内置模型；历史基线按版本号归档留存，既不要求人工日常盯屏逐个模型轮播，也不在每次常规代码推送上挂载重型 GPU CI。

## 原版 GUI 截图

原版参考客户端同步支持 GUI 对照抓图开发指令：`gui_open` 在受保护的虚空实验场景中打开真实的原版女仆菜单，`gui_status` 查询当前打开的窗口与槽位摘要，`gui_capture --name name.png` 则在当前渲染帧末尾保存真实的屏幕截图。
该流程绝不篡改原版 GUI 类，也不尝试在 Minecraft 1.20.1 中加载移植版模组；参考端身份观察清单为此扩充纳入了原版主界面与菜单容器类，而已归档的动画冻结包继续锚定其原有的工具身份版本。
参考客户端窗口尺寸显式固定为 `1280×720`，GUI 视觉对照统一采用简体中文与界面缩放倍率 `2`；当前语言、悬浮提示、鼠标指针位置、女仆模型、预览姿态与各开关状态均须结合 `gui_status` 返回的实测字段交叉确认。首次设置测试女仆状态后，必须等待客户端完成实体数据同步再调用 `gui_open`，避免原版界面按钮在实体同步包到达前按旧状态完成初始化而被误判为跨版本移植差异。每次 `gui_capture` 均返回原始 PNG 的 SHA-256 及同帧窗口/槽位快照；背景静态排版、女仆动态预览窗、版本号字样与跨版本物品图标须分项核对，任一部分未对齐均不得宣称 GUI 视觉对照通过。
